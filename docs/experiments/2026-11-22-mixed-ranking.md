# 用語選択の順位混合と取りこぼし分析

## 結果

第1版・本人用を優先する順位と得点順を2:1で交互に混ぜる方式を選んだ。ASRヒントと整形候補の両方で、valの正解率が旧mainを下回らず、1:1よりtest-novelの正解率が高かった。test-novelの上位16語では、旧mainの61.2%から64.2%へ上がった。

ASRと整形までのMetal実行は行っていない。PMが実機で再実行する。

## 評価条件

保存済みの1回目のASR出力から用語選択だけを再計算した。test-novelは500発話の正解500語、valは1,000発話の正解1,427語、dev-userは100発話の正解67語を分母とした。valを比率選択の判断に使い、test-novelで効果を確認し、dev-userは悪化確認だけに使った。

旧mainは優先辞書先行で、一字英字の発音別名を加える前の選択を再現した。得点順と交互方式は、`rバリュリファレンス`のような一字英字の読みを含む。

ASRのヒントは実際の呼び出し経路に合わせ、選択候補を先に20語へ絞り、続いて16語・240文字に制限した。整形候補は上位20語とした。正解外は各発話の正解語リストにない表記の件数であり、意味的に無関係かを人手で判定した値ではない。短い読みの内側一致は、正解外候補のうち2仮名の読みが正規化後の文字種区間の内側だけに一致した件数である。

## 比率の選択

交互2:1では、valのASRヒント正解率が旧mainより1語多く、整形候補も5語多かった。交互1:1は整形候補のval正解率を保ったが、ASRヒントは11語少なかった。したがって、両方のval正解率を旧main以上に保つ交互比率は2:1だけだった。

test-novelでは、交互2:1のASRヒント正解率は旧mainより16語（3.2ポイント）高く、整形候補は8語（1.6ポイント）高かった。交互1:1は2:1よりtest-novelの正解率がASRで0.8ポイント、整形で1.0ポイント高いが、valのASRヒント正解率が旧mainを下回る。得点順はtest-novelの正解率が最も高い一方、valはASRで79.0%、整形で80.7%となり、旧mainを下回った。

交互2:1の正解外候補はtest-novelのASRヒントで旧mainより22件減り、整形候補は同数だった。valではASRヒントの正解外が31件増え、整形候補は5件減った。短い読みの内側一致はvalのASRヒントで旧mainと同数、整形候補で1件減った。test-novelではASRで1件、整形で1件増えた。正解率を保つ条件ではあるが、正解外候補すべてが減るわけではない。

2:1の上位16語の正解ヒット率はval 1,203/1,427 (84.3%)、test-novel 321/500 (64.2%)、dev-user 60/67 (89.6%)だった。ASRの240文字制限を加えるとtest-novelは319/500 (63.8%)となる。

## 上位32語に入らなかったtest-novel語

交互2:1で上位32語に入った正解は362/500 (72.4%)、入らなかった正解は138語 (27.6%)だった。取りこぼした正解語は次の優先順で一つの型に分類した。分類は読みと表記の文字列に基づくヒューリスティックで、音声を聞いた判定ではない。

| 型 | 件数 | 1回目の出力の例（正解語 → 出力部分） | 一般規則で拾える見込み |
|---|---:|---|---|
| ひらがな・混在仮名に読みが残る | 3 | Stacked Hourglass Network → `スタックとアーワグラスネットワーク`（novel-000011）／chan → `ちゃん`（novel-000060）／Kotlin Coroutines → `ことりんこルーチン`（novel-000118） | ひらがなをカタカナへ正規化する照合で拾える可能性がある。短い一般語との衝突をvalで確認する必要がある。 |
| 読みが1〜2モーラ違う、または一部が残る | 3 | TensorFlow.js → `テンソルフロージェース`（novel-000077）／yarn remove → `ヤーノンルムーブ`（novel-000181）／window.onload → `ウィンドウロード`（novel-000443） | モーラ単位の近似照合で一部を拾える可能性がある。許容差を広げると誤候補が増えるためvalでの確認が必要。 |
| 英字の複数語が分かれて出る | 6 | Meta Quest Pro → `meta qst pro`（novel-000209）／VPC Endpoint Service → `vpc&pontサービス`（novel-000292）／Google Cloud Tasks → `google coudt`（novel-000398） | 語順を保つtoken単位の照合が候補になる。一般的な短いtokenによる誤候補を確認する必要がある。 |
| 英字の綴りが崩れる | 36 | iPerf3 → `ipaf3`（novel-000025）／ANSI SQL → `ancsql`（novel-000029）／Google Calendar → `google kerinder`（novel-000150） | 正規化後の編集距離で拾える可能性があるが、誤候補の増加リスクが高い。 |
| 数字が算用数字で出る | 5 | Garmin Forerunner 965 → `ガーミンフォアランナー965`（novel-000019）／Fusion 360 → `フュージョン360`（novel-000109）／ROUGE-1 → `ルージュ1`（novel-000303） | 数字表記と読みの対応付けが候補になる。数字の読み方が複数ある場合の誤候補を確認する必要がある。 |
| 上記基準に当たらない残り（漢字化などを含む） | 85 | Jina → `地名`（novel-000005）／Toyota → `豊田さん`（novel-000097）／W-OLED → `wort`（novel-000010） | 表記だけでは安定して拾える手掛かりがない。漢字の同音語や大きな音崩れを一律に救う規則は見込めない。 |

分類は例のIDを含めて評価スクリプトで再計算できる。上位32語の取りこぼしに対する救済規則は、この変更では実装していない。

## 選択時間

索引構築を除き、32候補を返す選択呼び出しを計測した。交互2:1の中央値は3.3〜3.6 ms/発話、p90は9.2〜13.3 ms/発話だった。評価環境での選択部分は20 msを下回った。音声認識や整形の時間は含まない。
