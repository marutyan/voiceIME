# Haas-ja-v1.0の英字技術用語追加学習（2026-11-21〜22）

## 目的と判定方法

用語ヒントを渡さないHaas-ja-v1.0が、技術用語を英字で出力できるよう追加学習できるかを試す。従来の本人録音では、用語集から除いた語の英字表記は0/20だった（[`2026-11-21-unseen-terms-baseline.md`](2026-11-21-unseen-terms-baseline.md)）。目標は、10秒の発話で約0.1秒の速さを保ちながら用語の正答率を上げること。

学習後モデルと元モデルを、valの固定200件で比べた。推論には用語ヒントを渡さず、正解は`spoken_text`とした。CERは`voiceime.eval`の読み揃え処理を通し、用語の英字表記率は同モジュールの`calculate_term_accuracy`で集計した。

## 追加学習方式と語彙

[Haas-ASR公式リポジトリ](https://github.com/third-intelligence/Haas-ASR)の取得時点のcommit `acc614f68769dcbfae9dba96b48439c4a66295af`には、追加学習用スクリプトを見つけられなかった。モデルをNeMoの`EncDecRNNTBPEModel`として復元し、[NeMoのASR fine-tuning手順](https://docs.nvidia.com/nemo/speech/nightly/asr/fine_tuning.html)にある`speech_to_text_finetune.py`を使った。汎用スクリプトは抽象クラス`ASRModel`を復元しようとするため、facultyの作業用コピーで`EncDecRNNTBPEModel.restore_from`を使うよう直した。Haas固有コードやリポジトリのソースは変更していない。

[モデルカード](https://huggingface.co/third-intelligence/Haas-ja-v1.0)のSentencePiece語彙は3,072語で、byte fallbackを含む。トークナイザーを展開してGPU、FastAPI、Hungarian Matchingなどを符号化し、ASCII英字を表現できることを確認した。すべてのASCII英字はbyte fallbackで表現できるため、英字表記のための語彙追加は要らない。既存語彙を保てばdecoderとjointの学習済み重みを維持できる。語彙を変える場合は出力層の形が変わり、NeMoの手順に従ってdecoderとjointを除外して読み込む必要がある。トークナイザーは英字を符号化できる。今回は英字表記を選ぶ確率が十分に学習されていないと判断し、語彙をそのまま使った。

## 環境とデータ

作業はfacultyの`~/voiceime-work-haasft/`だけで行った。Haas-ja-v1.0の`.nemo`はfacultyから直接取得し、revision `660728d39019e5e065046154beca44ac9a66a540`、SHA-256 `c6ed38698300a371a86eadab4b56d5458f47623f7fc4a5f1e938b5adbe8458aa`を記録した。音声や重みをMacからfacultyへ送っていない。

環境はPython 3.12.3、NeMo 2.7.3、PyTorch 2.14.0+cu126、Numba-CUDA 0.30.4。H100のdriverはCUDA 12.8対応で、初期に入ったcu130版PyTorchは動かなかったためcu126版へ替えた。NeMoの`cu12`追加依存を入れ、タスク環境内のCUDA 12ライブラリを参照させた。Numba-CUDA 0.30.4が`numpy.row_stack`を使う一方、初期のNumPy 2.5.3にはその属性がなかったため、NumPy 2.3.5に合わせた。CUDA 13の残存パッケージはCUDA 12環境の読込を妨げたため、作業用環境から外し、CUDA 12のwheelを再配置した。これらはfacultyの作業用仮想環境だけの変更で、リポジトリの依存定義やlockfileは変更していない。

`data/tts/train/manifest.jsonl`は9,990行あり、そのうちfacultyで読めた音声3,340件を使った。6,649件は未配置、1件は読み込みエラーだった。NeMoの記録では使用音声は10.50時間。タスク開始時に示された3,315件より25件多く、その時点で読めた分をすべて使った。正解文は`spoken_text_mixed`。

valの1,000件はすべて読めた。うち800件を学習中の検証用、200件を最終評価用に分けた。200件はseed 0で固定し、学習には使っていない。マニフェストと生成物のSHA-256は`~/voiceime-work-haasft/data-metadata.json`にある。最終評価用マニフェストのSHA-256は`a9b30b1b6c2b5772452a380a2c639c334eda3ba5b3b4c782959ca6f7244d76b7`。

## 学習設定と実行

| 項目 | 設定 |
| --- | --- |
| 学習データ | 3,340件、`spoken_text_mixed` |
| tokenizer | 既存の3,072語を維持、`update_tokenizer=false` |
| GPU | GPU3を単独使用、`CUDA_VISIBLE_DEVICES=3` |
| train / validation batch size | 16 / 16 |
| gradient accumulation | 1（実効batch size 16） |
| optimizer learning rate | `1e-5`、schedulerなし |
| epoch / precision | 1 / `bf16-mixed` |
| DataLoader | 8 workers、`pin_memory=true`、`max_duration=31.0` |

学習は2026-11-22 00:32ごろに開始し、209/209 stepsを約3分36秒で終えた。NeMoの検証800件では`val_wer=1.02415`。checkpointは`~/voiceime-work-haasft/exp/haas-ft-1epoch/2026-11-22_00-32-35/checkpoints/haas-ft-1epoch.nemo`（約2.3GB）と`.ckpt`に保存した。作業終了時に自分の学習・評価プロセスが残っていないことを確認した。

初回のbatch 16試行では、GPU2に別プロセスがある状態で起動し、そのプロセスが66.01GiBを使用していた。空き2.51GiBに対し6.39GiBの確保を要求してOOMになった（1分08秒、0/209 steps）。他のプロセスは停止していない。後続の起動試行ではNeMo用CUDAライブラリ不足、NumbaのGPU能力判定、NumPyの互換性で停止した。修正後のbatch 16実行では、最初のNumbaコンパイルに約1分54秒かかり、GPU使用率が一時0%になった。コンパイル後の観測では26〜100%の範囲で推移し、Numbaからgrid size 1、12、16の低占有率警告が出た。GPUが90%前後で飽和したとは確認できていない。CUDA利用時間は、成功した学習実行がGPU3で約5〜7分、評価が1分16秒未満。学習プロセスの厳密な終了時刻は記録していない。

## val 200件の結果

| モデル | 読み揃えCER（`spoken_text`基準） | 用語の英字表記 |
| --- | ---: | ---: |
| 元のHaas-ja-v1.0 | 9.48% | 1/278（0.36%） |
| 1 epoch追加学習後 | 24.56% | 0/278（0%） |

追加学習後はCERが15.08ポイント悪化し、用語の英字表記も改善しなかった。今回の設定では目標を達成できず、このcheckpointを精度改善版として採用する根拠はない。結果JSONは`~/voiceime-work-haasft/eval/metrics.json`、各出力は同ディレクトリの`baseline-hyp.jsonl`と`finetuned-hyp.jsonl`にある。

評価の処理時間は、元モデル11.26秒、追加学習後1.89秒だったが、モデル順が固定でwarm-upを入れていないため、初回のCUDAカーネル準備時間が元モデル側だけに含まれた可能性がある。両者の比較値として使わない。10秒の発話をspeech.cppで処理する0.1秒の目標も、学習後重みをspeech.cppへ変換してMac上で測っていないため未確認。

## 次の提案

今回のcheckpointは採用せず、残りの学習音声がfacultyに揃った後に、同じval splitと評価コードで再試行する。次の試行では、学習データ量とlearning rateまたは学習対象層のどれを変えるかを先に決め、一度に一条件だけ変える。これらは学習条件の変更に当たるため、次の実行前に条件を決める必要がある。GPU使用率の平均が目標に届くかも、warm-upとデータ読み込みを分けて記録する。
